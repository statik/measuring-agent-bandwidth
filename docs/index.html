01 Verdict
Verdict

The AI assistant is not the bandwidth story.

We measured a 20-student, 6-hour hands-on workshop built around Posit Assistant. The one-time installer and package downloads move 33.66 GB. The AI assistant — every conversation, every student, all day, modeled from token metadata of 597 real agent sessions — moves 385.78 MB. That is about 1% of the total, an average of 0.14 Mbps across the whole room.

What Room total Per student Character
One-time downloads (installers + packages) 33.66 GB 1.68 GB Plan for this burst
AI assistant traffic, entire 6-hour session 385.78 MB 19.3 MB Background noise
If all 20 assistants stream a response at the same instant 0.39 Mbps 0.02 Mbps Less than one video call

This memo presents the numbers, the method behind them, and netimpact — a reusable tool instructors can run against their own workshop to produce a one-page PDF report for venue staff. See the example report.

The verdict for this workshop is MODERATE — entirely because of the installers. If attendees install before arriving, it drops to a load the venue will never notice.
For venue staff

Provision for one download burst, then relax

If your network handles attendees browsing the web and checking email, it handles the AI assistant portion of this workshop without any special provisioning. The only event worth planning is the one-time installer download, and it is bounded and schedulable.

One assistant conversation ≈ 2.7 MB — about the same as loading a news homepage or two.
One student's entire day ≈ 19 MB — about half a minute of HD video streaming.
The whole room's entire day ≈ 386 MB — about half an hour of a single video call.
Assistant traffic is steady and tiny, not bursty and large: small uplink requests and a trickle of streamed text. It does not compete with the download burst; it disappears inside it.
Worked example

A 20-student Posit Assistant workshop, measured

The scenario follows the published getting-started material: students install Python, R, Positron, and RStudio at the venue (half macOS, half Windows), install the querychat and shinychat packages in both languages, have their first conversation with Posit Assistant, work through querychat natural-language data exercises, and lean on the assistant for debugging and dashboards all afternoon. Assistant traffic

Why chat traffic is measured in megabytes, not gigabytes

An AI assistant conversation is text moving in two directions. Chat APIs are stateless, so every round trip re-sends the conversation so far — uplink grows quadratically with conversation length — while the response streams back as a trickle of tokens. netimpact models this directly: 4 bytes per request token, 30 bytes per streamed token (SSE framing included), 1.08× protocol overhead, and multiple API round trips per agentic turn.

Activity (per the workshop script) Per conversation Per student Room total
First conversation with Posit Assistant (16 round trips) 2.68 MB 2.68 MB 53.57 MB
querychat exercises — natural-language SQL over data 321.84 KB 643.68 KB 12.87 MB
General assistant use: debugging, plots, dashboards (4 conversations) 3.99 MB 15.97 MB 319.33 MB
Uplink: ~4 bytes per token Tokenizers average ~4 characters per token for English and code; request bodies are uncompressed UTF-8 JSON, so bytes ≈ characters. Verifiable by dividing a payload's JSON length by its token count.
Downlink: ~30 bytes per streamed token Streamed responses arrive as server-sent events; each delta wraps a few tokens of text in a JSON envelope plus SSE framing. Verifiable with mitmproxy: response bytes ÷ output tokens from the provider's usage block.
Statelessness and caching Chat APIs document that each request carries the full message history, and prompt caching caches server-side compute — the prompt still crosses the wire. Uplink therefore grows quadratically with conversation length, which the model sums exactly.
Conversation shapes — calibrated The agentic blocks take their parameters from aggregate token metadata of 597 real coding-agent sessions (median: 21 round trips, 24k-token starting context, ~330 output tokens per response; median session ≈ 4.4 MB on the wire). The querychat block follows that tool's one-request schema-to-SQL design.

The shapes are calibrated, deliberately generous, and the conclusion is insensitive to them: even a 10× modeling error puts the room at 3.9 GB — still about a tenth of the download burst. Every constant, the calibration procedure, and its grounding are documented in METHODOLOGY.md.

Provider-side prompt caching reduces cost and latency, not network transfer: the full conversation still crosses the wire on every round trip. The model accounts for that.
Methodology

Measured where it matters, modeled where it doesn't

Installers — measured HTTP HEAD requests against the publishers' own CDNs (python.org, CRAN, Posit) report exact transfer sizes. URLs are resolved to the current release at run time, with sizes recorded on 2026-08-17 as a fallback.
Packages — measured PyPI dependency trees are walked through requires_dist metadata using the largest platform wheel per package (conservative); uv.lock files carry exact recorded sizes; R packages are sized against CRAN's binary repository.
Assistant — modeled Token-level model of stateless chat APIs. Modeling is appropriate here because the quantity is so small that no plausible modeling error changes any venue decision.

Scale math is transparent: per-item size × students × share gives room aggregates, and the burst table assumes shared Wi-Fi delivers about 70% of the advertised link speed to actual downloads. To validate against real traffic before an event, proxy the IDE through mitmproxy and read per-host byte counts while running the workshop script once, use nettop (macOS) or Resource Monitor (Windows) for per-process totals, or compare a pilot student's access-point byte counter against the per-student column.

Not counted: OS updates, video streaming, and general browsing — venue baselines that exist with or without the workshop.
The tool

netimpact: point it at your workshop, get the report

netimpact is a Shiny for Python app that deploys to Connect Cloud as-is. Give it a GitHub project and it scans the tree for renv.lock, uv.lock, manifest.json, and requirements.txt files, merges the package sets across exercises, and sizes them against the live indexes. Pick the installers, a platform split, and an assistant-usage preset; download the venue report as PDF, Typst source, or JSON. A CLI produces the same report from a scenario file: 

[workshop]
name = "Posit Assistant Workshop"
students = 20
duration_hours = 6

[installers]
products = ["python", "r", "positron", "rstudio"]
mac_share = 0.5

[[pypi]]
packages = ["querychat", "shinychat"]

[[repos]]
url = "posit-conf-2024/ds-workflows-r"   # scanned for lockfiles

[assistant]
preset = "half-day-workshop"

Scanning a real workshop repository works today: pointing the tool at posit-conf-2024/ds-workflows-r found renv.lock and manifest.json files across nine exercise folders, merged them to 229 R packages, and sized 216 CRAN binaries at 357 MB per student.

Repository: statik/measuring-agent-bandwidth. Set GITHUB_TOKEN on the deployed app to raise the GitHub API rate limit.
Playbook

Three ways to shrink the burst to zero

The download burst is the only load worth managing, and it is the easiest kind of load to manage: it is one-time, known in advance, and entirely schedulable.

1. Pre-install Send install instructions a week ahead. Every student who arrives ready removes ~1.7 GB from the venue burst. This is the highest-leverage email an instructor sends.
2. Stagger Run the install step in waves during registration or a break rather than as a single "everyone click now" moment. Four waves of five students quarters the peak.
3. Bring it with you Installers on USB drives, or a local package cache/mirror on the venue LAN, take the WAN out of the picture entirely. The report's per-item table is the packing list.
None of these techniques are needed for the assistant itself. There is nothing to stage, cache, or schedule for 0.14 Mbps.
Sources and caveats

Evidence, confidence, and what could drift

High confidence — download sizes Measured 2026-08-17 by HTTP HEAD against python.org (3.14.7), CRAN (R 4.6.1, macOS sonoma-arm64 and Windows binaries), Posit's CDN (Positron 2026.08.1-2), and download1.rstudio.org (RStudio 2026.08.0). PyPI and CRAN package trees resolved from live index metadata the same day.
Modeled — assistant traffic Token constants (4 B/request token, 30 B/streamed token, 1.08× overhead, 75 tok/s streaming) are stated in every report and in netimpact/engine.py. Conversation shapes come from the published workshop scripts, calibrated against aggregate token metadata from 597 real agent sessions via netimpact.calibrate — token counts only, no conversation content.
Caveat — release drift Installer sizes grow between releases. netimpact re-resolves current URLs at run time, so regenerate the report in the week before an event rather than reusing an old PDF.
Caveat — usage variance A student who pastes a large dataset into chat sends more than the model assumes. The gap that matters is bounded: even 10× the modeled assistant traffic is 3.9 GB for the room — still about a tenth of the download burst.
Sources reviewed: assistant.posit.co getting-started, posit-dev.github.io/querychat and /shinychat, PyPI and CRAN index metadata, publisher CDN headers, and posit-conf-2024/ds-workflows-r as a live scan subject. Generated with netimpact 0.1.0; all figures reproducible via uv run python -m netimpact scenarios/posit-workshop.toml.
